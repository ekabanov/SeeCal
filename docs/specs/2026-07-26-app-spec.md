# SeeCal iOS App Spec (extracted from interactive prototype, 2026-07-26)

Source of truth for product behavior: the interactive prototype
(https://claude.ai/code/artifact/beb200b6-0c01-4ef3-a05f-5bb739aa7336) as iterated with
the user on 2026-07-26. This document translates it into implementable requirements
against the existing SwiftPM package `ios/SeeCal` (targets: SeeCalDomain,
SeeCalInference, SeeCalPersistence, SeeCalApp). Where this spec conflicts with existing
code (models, drafts, view models), THE SPEC WINS — evolve the existing types, do not
build a parallel world.

## 0. Constraints inherited from the ML pipeline (non-negotiable)
- Inference: on-device via the existing `MLXQwen35RunnerBuilder`/`InferenceRuntime`
  path (base 4-bit model + LoRA adapter via LoRAContainer, fused at load). No cloud.
- Prompt: existing `QwenPromptBuilder` byte-parity rules stay (no system message; when
  depth lands, the exact variant-B line — see depth design brief section (f)).
- Model output schema: `total_calories, protein_g, fat_g, carbs_g,
  items[{name, estimated_grams, calories, protein_g, fat_g, carbs_g}]`.
- Inference latency is 15–30 s on device: the wait is a designed experience (§5).
- Weights are BUNDLED in the app (user decision; fits Apple's 4GB cap). No downloader.

## 1. Information architecture
Five-slot tab bar: **Today · History · [Scan] · Profile · Settings**.
- Scan is the center slot: a raised 64pt circular FAB in the brand color, camera
  glyph, label "Scan"; it overhangs the bar by ~36pt with a bg-colored halo ring.
- The tab bar hides completely while the camera is open.
- All screens scroll vertically with bottom clearance for the bar + FAB overhang.

## 2. Domain model & goal calculation
### UserProfile (evolve `ProfileModels.swift`)
`sex (male|female)`, `dateOfBirth: Date`, `heightCm: Int`, `weightKg: Double`,
`activity ∈ {sedentary, light, moderate, active}`,
`weeklyRateKg: Double` in **[−1.0 … +0.5]**, default −0.5, step 0.1.

### Goal (pure function; replaces manual goal editing — GoalEditDraft is retired)
```
BMR  = 10·kg + 6.25·cm − 5·age(years) + (male ? +5 : −161)        // Mifflin-St Jeor
TDEE = BMR × factor   // sedentary 1.2, light 1.375, moderate 1.55, active 1.725
goal = max(1200, round10(TDEE + weeklyRateKg × 7700 / 7))
```
Reference vector for tests: male, dob 1988-03-14 (age 38 on 2026-07-26), 183 cm,
78.4 kg, moderate, −0.5 kg/wk → BMR 1743, TDEE 2701, **goal 2150**.
Macro targets from goal: fixed split 30/25/45% of kcal → grams via 4/9/4 kcal/g.
Recommended weekly-rate band: **−0.75 … −0.25** ("lose"); outside band shows a
warning (below −0.75: "Faster than 0.75 kg/week is hard to sustain and not
recommended."; above +0.25: "Gaining faster than 0.25 kg/week mostly adds fat.").

### MealEntry (evolve `TrackingModels`/`PersistenceModels`)
`id, name, timestamp, photo (file reference), items: [MealItem]`, optional
`volumeMl: Double?`, `maxHeightMm: Double?` (depth metadata, nil until D5 lands).
`MealItem = {name, grams, base: {grams, kcal, protein, fat, carbs}}`; current
nutrition scales linearly: `value = base.value × grams / base.grams`.
Entry totals = sum of scaled items. **Migration**: existing persisted entries without
items load as a single synthetic item carrying the entry's stored totals (base =
stored values); persistence keeps the `.bak-<ts>` corruption behavior.

## 3. Onboarding (first launch only: no persisted profile)
Full-screen, 6 steps, progress dots, Back (hidden on step 1) + Continue buttons,
"Skip for now" (step 1 only → defaults from §2 reference profile minus name).
1. **Welcome** — camera glyph, copy: point camera → calories/macros/portions on this
   iPhone; "A few details set your daily calorie goal. You can change everything later
   in Profile."; privacy note: "Meals are analyzed on your iPhone — nothing is uploaded."
2. **About you** — sex chips; birthday date picker with live "N years old" subtitle.
3. **Your body** — height stepper (±1 cm, 120–230), weight stepper (±0.5 kg, 35–250).
4. **Activity** — 4 option cards with descriptions (Sedentary "Desk job, little
   exercise" / Light "1–2 workouts a week" / Moderate "3–5 workouts a week" /
   Active "Daily training or a physical job").
5. **Weekly target** — slider −1.0…+0.5, step 0.1, live label ("−0.5 kg / week",
   kind LOSE WEIGHT/MAINTAIN/GAIN WEIGHT), recommended band visually highlighted on
   the track, warning note when outside band.
6. **Your daily goal** — big kcal number + transparent math line
   ("BMR 1,743 × 1.55 (moderate) = 2,701 kcal burned − 550 kcal (−0.5 kg/wk) =
   2,150 kcal"), button "Start tracking" → persist profile, land on Today.

## 4. Today
- Header: uppercase weekday+date subtitle, "Today" large title.
- Ring card: animated circular progress (consumed/goal kcal, number centered,
  "of N kcal" beneath) + three macro bars (Protein/Fat/Carbs, "consumed / target g",
  each in its macro color).
- MEALS section: rows = photo thumbnail (52pt rounded), name, "HH:mm · N g protein",
  kcal, chevron. Tap → edit sheet (§6, edit mode). Rows are buttons with proper
  styling (no default chrome).
- Privacy chip (brand-tinted): "Analyzed entirely on this iPhone."
- Only today's entries counted/listed (existing day-filter logic stays).

## 5. Scan → Analyzing → Result
### Camera (full-screen, tab bar hidden)
- Live preview; close (✕) top-left returns to Today.
- Guidance overlays (coaching, never gating — shutter always enabled):
  distance chip ("38 cm · in range" green when 35–45 cm, else "move closer"/"back up
  a little" amber — requires depth/LiDAR; hide chip on non-LiDAR devices),
  level indicator (bubble centers when device is flat, from gravity vector),
  "LiDAR depth · capturing portion size" pill when available,
  hint text ("Hold flat over the plate" → "Framed — capture when ready").
- Behind a `CaptureService` protocol; simulator/mock implementation returns a bundled
  sample photo so the whole flow runs in tests and simulator.
### Analyzing
- Captured photo card with animated scan line (respect Reduce Motion).
- Staged checklist reflecting the real pipeline, each stage checking off:
  1. "Measuring portion depth" → done-subtitle "Portion measured · ~V ml, H mm tall"
     (stage omitted entirely on non-LiDAR / until D5 lands),
  2. "Identifying foods" → "N foods found: a, b, c",
  3. "Estimating nutrition" → "Done".
  Stages 2–3 check off when real inference completes (single model call; stage
  animation is presentational, driven by actual runtime state).
- **Navigation away does NOT cancel inference.** On completion: if the Analyzing
  screen is frontmost → present result sheet; otherwise show a persistent brand-color
  banner above the tab bar: "✓ Meal analyzed — tap to review" → opens the sheet.
  A new scan clears any pending banner. NOTHING is persisted without explicit confirm.
- Inference errors surface in the same staged UI with a retry affordance (reuse
  existing error surfacing from InferenceRuntime).
### Result sheet (bottom sheet, also the meal EDIT sheet)
- Header: photo thumb, meal name; when depth metadata present: "depth-assisted" chip +
  "~V ml · max height H mm" meta line (hidden otherwise/in edit of depthless meals).
- Hero: total kcal (large, tabular) + "typically ±12%" range hint.
- Macro chips: protein/fat/carbs grams in macro colors.
- "DETECTED ITEMS — ADJUST IF NEEDED": one row per item — name,
  "Np · Nf · Nc" subtitle, gram stepper (±5 g, min 5, live linear rescale of that
  item and the totals), item kcal.
- Footnote: "Estimates come from the on-device model. Adjusting grams rescales an
  item's nutrition proportionally."
- Actions — new scan: [Discard → back to camera] [Log meal → persist, toast "Logged
  to Today", switch to Today scrolled to top]. Edit mode (opened from a meal row):
  [Cancel] [Save changes → update entry, toast "Changes saved"].
  (Evolve existing `MealEditDraft`; one draft type serves both modes.)

## 6. History
- Segmented control: **Week · Month · 6 months**.
  Week = 7 daily bars w/ day labels; Month = 30 daily slim bars, labels every 7 days
  ("−28d…now"); 6 months = 26 weekly-average bars, month labels, "now" last.
- Bars colored by adherence vs goal: ≤1.05× green (brand), ≤1.25× amber, else red;
  unlogged days neutral; today outlined. Dashed goal line with a chip label
  ("goal 2,200") that bars cannot strike through. Legend: on target / >5% over /
  >25% over. Labels live in a reserved axis zone below the bars — never overlap bars.
- Stats row: avg kcal/day, days logged (of range), avg protein.
- Below: recent meals list (same row component as Today).
- Aggregation from the real meal log via `ProgressModels`/aggregator (evolve).

## 7. Profile
- Header card: initials avatar (brand circle), name, "Logging since <month year>".
- Body card: Birthday (date picker + "N years" note), Sex chips, Height stepper,
  Weight stepper (+ trend note from weight log, e.g. "−1.2 kg this month").
- Lifestyle card: Activity chips; Weekly target slider (same component as onboarding).
- Daily goal card: big kcal + transparent math line + "Macro split 30 · 25 · 45 %" row.
- Every change recomputes the goal immediately and updates Today's ring/bars.

## 8. Settings
- **Sync** card: "iCloud sync — Meals, weight and goal on all your devices" and
  "Apple Health — Write meals, read weight & workouts", both with a "SOON" badge
  (disabled roadmap rows; no functional toggles; copy must not claim sync exists).
- **Capture** card: "Use LiDAR depth — improves portion-size accuracy" toggle;
  "Capture coaching — distance & level guides" toggle.
- **On-device model** card: "Qwen3.5-4B · SeeCal adapter <version>" + ON DEVICE badge;
  subtitle: quantization, fine-tune provenance, "typical calorie error ±12%",
  "Photos are processed locally and never uploaded." Version strings read from the
  bundled model/adapter config, not hardcoded.

## 9. Design system — THE PROTOTYPE IS THE VISUAL SPEC
The committed prototype (`docs/design/prototype/seecal-prototype.html`) is the
binding visual reference (user directive 2026-07-26: "design must follow prototype").
Anyone implementing a screen MUST open that file and read the markup + CSS for the
corresponding screen (`#scr-today`, `#scr-camera`, `#scr-analyzing`, `#scr-history`,
`#scr-profile`, `#scr-settings`, `.sheet`, `.onboard`, `.tabbar`) and reproduce its
layout, spacing, hierarchy, copy, and component appearance in SwiftUI — same card
shapes, same type scale relationships, same colors (tokens below are extracted from
it), same chart/slider/stepper appearance. Deviations only where iOS platform
conventions demand it (e.g. native date picker), and they should be noted in the
task report.
- Brand "basil" green (light #1F7A52 / dark #43C98B), soft tint (#E3EFE8 / #12281D);
  macro colors protein #C2495E/#E0728A, fat #D99A2B/#E6B45A, carbs #4E79C7/#7D9FE0;
  danger #C0392B/#E4685A. App bg/card follow system (systemGroupedBackground-like:
  #F6F7F5+white light, black+#1C1C1E dark). Full dark-mode support.
- System font; large rounded cards (18pt radius), soft elevation; tabular numerals
  for all nutrition figures; uppercase letter-spaced section labels.
- Respect Reduce Motion for the ring animation, scan line, and stage pulses.
